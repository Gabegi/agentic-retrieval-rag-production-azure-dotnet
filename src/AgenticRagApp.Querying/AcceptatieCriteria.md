# Acceptance Criteria

Business requirements for the chatbot's answering behavior. Not yet implemented/validated
against `AgenticRagQueryService` and related services in this project.

1. ~~All answers are generated in C1-level Dutch.~~ **Changed 2026-08-12 to B1-level Dutch** — plain
   language so the whole workforce can follow it, not just policy authors. Implemented in
   `KnowledgeService.AnswerInstructions`. **Needs PO sign-off**, since this rewrites the criterion as
   originally agreed; the golden-questions expected answers may also need rewording to match.

2. The chatbot gives NO medical advice — clear fallback message.

3. The chatbot gives NO opinion.

4. The chatbot catches prompt injections.

5. The chatbot must not use personal information (such as address, BSN/national ID, names) of
   clients — neither in the question nor in the answer.

6. When there is no relevant answer (grading to be determined by the PO), a clear message is
   shown.

7. Source attribution of all documents used is shown in the format: `[Title] - p.(page number)`

   E.g.: `[Vilans protocollen voor neustampon] - p.2`

   AND clickable, so the end user is navigated straight to the document.

## Background

The answer is not generated by our own chat-completion call — it's generated by the Azure AI
Search **agentic retrieval / knowledge base** (`AnswerSynthesis`), configured in
`AgenticRagApp.Infrastructure/Clients/Search/KnowledgeService.cs`
(`RetrievalInstructions` / `AnswerInstructions`). `AgenticRagQueryService.AskAsync` (this
project) only calls that knowledge base and processes the result — there is no prompt of our
own in between.

This means two distinct places for change, depending on what's being enforced:

- **`KnowledgeService.cs`** (`AgenticRagApp.Infrastructure`) — the actual answer-writing prompt.
  Editing `RetrievalInstructions` / `AnswerInstructions` covers anything that's just "tell the
  model to behave differently": criteria **1, 2, 3, 6**, and the wording part of **7**. No new
  code, just better instructions to the managed Azure service.
- **`AgenticRagQueryService.cs`** (`AgenticRagApp.Querying`) — our own code, running before the
  question is sent to Azure and after the answer comes back. Instructions can be ignored or
  bypassed by a sufficiently clever prompt, so criteria that must hold *regardless* of what the
  model decides to do — **4 (prompt injection) and 5 (PII)** — need actual guard logic here, not
  just wording.

## Step-by-step change plan

### Step 1 — Prompt instructions in `KnowledgeService.cs`
Covers criteria 1, 2, 3, 6, and the wording of 7. Edit `RetrievalInstructions` /
`AnswerInstructions` in `EnsureKnowledgeBaseAsync`.

- **Option A — one combined instruction pass.** Rewrite both strings once with all five
  requirements folded in (language level, no medical advice + fallback text, no opinions,
  no-answer fallback, citation format).
  - *Implications:* fastest to ship, one eval-suite run to validate all five at once. Harder to
    isolate which line caused a regression if the model starts behaving oddly, and blocked
    end-to-end until the PO delivers the exact fallback text for #2 and the grading threshold
    for #6 (placeholders would have to be used and revisited).
- **Option B — incremental, one criterion per commit/PR.** Land 1, 3, and the #7 wording
  immediately (no open questions); hold 2 and 6 back until PO input arrives.
  - *Implications:* slower, more eval runs, but each change is independently verifiable and
    revertable, and doesn't block on PO. Recommended given #2 and #6 have open questions below.
- **Open question (PO):** exact fallback text for #2 (no medical advice); grading/threshold
  definition for #6 (no relevant answer). Both block final wording, not just a placeholder.

### Step 2 — Citation grouping fix in `AgenticRagQueryService.AskAsync`
Part of criterion 7. Currently citations are grouped `GroupBy(c => c.DocumentId)`
(`AgenticRagQueryService.cs:56-62`), keeping only `g.First().Page` — if the answer cites page 2
and page 5 of the same document, one page is silently dropped.

- **Option A — group by `(DocumentId, Page)`.** Minimal change to the existing `GroupBy`/`Select`.
  - *Implications:* straightforward, low risk, fixes the data loss directly. Slightly more
    `Citation` entries returned per answer (one per cited page instead of one per document),
    which is a (small) API response shape change any consumer needs to tolerate.
- **Option B — keep grouping by document, but carry a `Pages: int[]` list instead of a single
  `Page`.** Changes the `Citation` record shape instead of the grouping key.
  - *Implications:* fewer citation entries (still one per document), but changes the public
    `Citation` contract more (existing `Page` consumers need updating), and doesn't match the
    literal `[Title] - p.(page)` format as directly — that format is inherently per-page.
  - *Recommendation:* Option A, since requirement 7's format is explicitly per-page.

### Step 3 — Prompt injection guard (criterion 4)
New logic in `AgenticRagQueryService.AskAsync`, running on `question` before
`_client.RetrieveAsync` is called (line ~34-45).

- **Option A — heuristic/pattern-based guard.** New `PromptInjectionGuard` service with a
  regex/keyword check (e.g. "ignore previous instructions", role-manipulation phrases,
  system-prompt extraction attempts). On a hit, short-circuit with a fixed refusal message and
  skip the knowledge base call entirely.
  - *Implications:* cheap, fast, no extra external dependency or cost, ships quickly. Weak
    against novel/obfuscated injection phrasing (translations, encoding tricks) — will need
    ongoing pattern tuning as new attempts are observed.
- **Option B — Azure AI Content Safety "Prompt Shields".** Call the managed detection API before
  querying the knowledge base.
  - *Implications:* materially stronger detection, maintained by Microsoft, no in-house pattern
    list to maintain. Adds an external call (latency + cost) to every query, and a new
    dependency/config surface (endpoint, key, resource provisioning).
- **Option C — instruction-only ("ignore embedded instructions").** Just add wording to
  `AnswerInstructions` telling the model to ignore embedded instructions in documents or the
  user question.
  - *Implications:* zero engineering effort, but per the Background section above, this is
    exactly the kind of guarantee an instruction can't reliably provide — not sufficient on its
    own for an acceptance criterion phrased as "catches".
- **Recommendation:** A now (fast, no new dependency) + C as a defense-in-depth layer in Step 1;
  revisit B if the heuristic guard proves insufficient in practice.

### Step 4 — PII guard (criterion 5)
New logic in `AgenticRagQueryService.AskAsync`, checking `question` before the call and
`result.Answer` after it returns.

- **Option A — regex-based (BSN checksum, postcode+huisnummer patterns, etc.).** New
  `PiiGuard`/`PersonalDataFilter` service using hand-written patterns.
  - *Implications:* no external dependency, predictable and testable, but unreliable for names
    — Dutch names don't have a detectable pattern, so this option effectively can't cover the
    "names" part of criterion 5.
- **Option B — Azure AI Language PII Detection API.** Call the managed PII-detection service on
  both `question` and `result.Answer`.
  - *Implications:* handles names and other unstructured PII far better than regex, maintained
    externally. Adds an external call (latency + cost) per query, plus new
    dependency/config/data-residency considerations (question and answer text leave the process
    to be scanned) — worth a quick check with security/privacy given this touches client data
    directly.
  - *Recommendation:* Option B for names/addresses; can be combined with a fast local BSN-checksum
    regex (Option A) for the one category regex handles reliably, avoiding an extra external call
    just for that check.
- **Behavior on detection (applies to either option):** replace the answer with the fallback
  message rather than redacting in place — a redacted answer can read as incomplete or
  confusing, and redaction alone doesn't stop the question-side check from having already sent
  PII to Azure OpenAI as part of the query.

### Step 5 — "no relevant answer" threshold (criterion 6, enforcement half)
Once the PO defines the grading/threshold: add a check in `AgenticRagQueryService.AskAsync` (e.g.
on `initialChunks.Count` or a relevance score from `result.Activity`/`result.References`) that
overrides the synthesized answer with the fixed fallback text when below threshold.

- Blocked until PO input lands (see Step 1's open question) — the wording-only version from Step
  1 can ship first as an interim measure since the model may already decline reasonably often on
  its own; this step adds a hard guarantee on top.

### Suggested order
1. Step 1 (Option B, incremental) for criteria 1, 3, and 7's wording — no blockers.
2. Step 2 (citation grouping fix) — no blockers, small and isolated.
3. Step 3 (prompt injection guard, Option A + C) — no blockers.
4. Step 4 (PII guard) — needs a quick decision on Option A vs. B before starting.
5. Step 1's remaining pieces (criteria 2 and 6 wording) + Step 5 — once PO delivers the fallback
   text and grading threshold.
